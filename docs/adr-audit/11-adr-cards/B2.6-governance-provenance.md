# B2.6 — Governance & Provenance

**Zone:** B2.6 (macro layer M5 — Learning & Growth) · **Tier:** B · **Batch:** 2 (ADR-0051–0100) · **Card author:** Tier-B audit subagent · **`verified_at` SHA:** `cbfc8ccb`

This zone is a small sequential arc of three same-week ADRs (2026-05-21/22) that together define who may approve durable teaching content and where autonomous (non-operator) content is allowed to enter the pipeline: ADR-0092 builds a schema-checked reviewer identity/scope registry (`docs/reviewers.yaml`); ADR-0094 widens the teaching-proposal schema with a sealed, exhaustive-match `ProposalSource` type so every proposal (operator/miner/curriculum/…) carries typed provenance; ADR-0095 uses that provenance to let Phase-5 contemplation miners emit `PackMutationProposal` candidates without inventing a second admission path. Read together against `AGENTS.md`'s typed learning boundary (INV-21…24/29/30) and the sabotage-test discipline, the arc earns a mixed verdict. What is genuinely, verifiably true: `ProposalSource` is a real sealed type, required on every created proposal, exhaustively matched everywhere it is consumed, and has cleanly absorbed two more kinds since ADR-0094 landed (`contemplation` via ADR-0080, `exemplar_corpus` via ADR-0163.C) with no schema churn — exactly the outcome ADR-0094 promised. The identity-pack defense ADR-0095 specifies for miner findings is real and independently tested. Everything else claimed as a *safety* property is weaker than the ADR prose states, and — critically — it is weaker **identically for miner- and operator-sourced content**, not weaker for miner content specifically. The reviewer registry ADR-0092 builds is real and load-bearing, but for a narrower scope than ADR-0092's own Context section claims: it gates Domain Pack Contract validation (predicate P8) and expert-demo audit-passed claims, and is never imported or consulted anywhere under `teaching/` — meaning neither an operator's nor a miner's proposal is ever checked against `docs/reviewers.yaml` on the path this zone's own ADRs describe as "the reviewed teaching path." Separately, ADR-0095's own named replay-equivalence pre-gate is a no-op by default in production (`NoOpReplayChecker` always passes; the CLI entry point never supplies a real checker), and the `PackMutationProposal` objects both sources produce have no code path to actual pack admission at all — a distinct, structurally parallel proposal type (`TeachingChainProposal` + `ProposalLog`) is the one system in the repo that genuinely enforces replay-equivalence and an accept/reject/withdraw state machine, and nothing bridges miner/curriculum output into it. This is the same shape of finding Batch 1 raised for ADR-0014 (`AA-124`: `LearningArtifact` produced by `core_ingest/compiler.py`, consumed by nothing) — a real, tested, well-typed construction step whose output terminates before reaching the mechanism the ADR believed it was attaching to.

### 1. Content summary

- **Decision made:** Introduce a structured, validator-checked "Reviewer Registry v1" schema for `docs/reviewers.yaml` — a small, deliberately minimal set of fields (`reviewer_id`, `display_name`, `role`, `domains`, `review_scope`, `provenance`) resolved by the Domain Pack Contract v1 validator (ADR-0091 predicate #8). Ships with exactly one bootstrap reviewer (`shay-j`); adding more is itself a reviewed proposal. The validator refuses ratification on five named schema violations (bad `schema_version`, unresolvable `reviewer_id`, out-of-domain `role: domain` reviewer, out-of-scope `review_scope`, duplicate `reviewer_id`).
- **Alternatives explicitly rejected:** none named explicitly as rejected options; the ADR frames the alternative implicitly ("free-form list will produce drift") rather than naming a rejected design.
- **Artifacts the ADR claims will exist:**
  - `docs/reviewers.yaml` (`schema_version: 1`, bootstrap `shay-j` entry, self-sealed provenance)
  - `core/capability/reviewers.py` — immutable loader: unknown-key rejection, duplicate-id rejection, role/domain restrictions, review-scope checks
  - `core/capability/domain_contract_predicates.py` — registry consulted for ADR-0091 predicate P8
  - `evals/reviewer_registry/runner.py` — the reviewer-registry lane
  - `tests/test_capability_cli.py` and "the ratification tests" — ledger rows depending on successful reviewer resolution
  - Invariant `reviewer_registry_schema_v1` — malformed registry must fail loudly, non-zero exit, typed error, no ledger row emitted
  - Claim (Context section): the registry is "also load-bearing for proposal review (`teaching/review.py`)"

### 3. Liveness / integration

- Live on two real, reachable paths: (a) Domain Pack Contract v1 validation, predicate P8 (`core/capability/domain_contract_predicates.py:332`), reached whenever a pack contract is validated/ratified; (b) expert-demo audit-passed claim verification, `core/capability/expert_demo.py:320`'s `registry.can_review(claim.signed_by, domain_id=domain_id, scope="eval")`, reached during expert-demo promotion. - **Not** reached anywhere under `teaching/` — `teaching/review.py`, `teaching/store.py`, and `teaching/proposals.py` (the two proposal-review systems this zone's later ADRs extend) contain zero references to the registry, `ReviewerRegistry`, or `load_reviewer_registry`. Confirmed by exhaustive repo-wide grep (see §2 last row).
- **Sabotage test (two-part, as the parent task requested):**
  1. Delete/corrupt `docs/reviewers.yaml` → `load_reviewer_registry` raises `ReviewerRegistryError`; Domain Pack Contract P8 fails (`registry is None` branch, `domain_contract_predicates.py:343`); expert-demo claim verification fails closed (`_load_registry_for_expert_demo` in `core/capability/reporting.py:659` degrades to an empty registry, which makes every `can_review` check False). **Observable, load-bearing change** on both of those paths — this half is real.

This is the sharper form of the parent task's question: it is not that a miner-sourced proposal has a *weaker* path around the registry than an operator-sourced one — **neither has a path through the registry at all** on this specific flow.
