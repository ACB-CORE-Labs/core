# B2.7 — Demo/Showcase & Frontier Adapters

**Zone:** B2.7 (cross-cutting MV/M3) · **Tier:** B · **Batch:** 2 (ADR-0051–0100) · **Card author:** Tier-B audit subagent · **`verified_at` SHA:** `cbfc8ccb`

Three ADRs, two relationships. ADR-0082 is a standalone piece of *evaluation instrumentation*: a provider-adapter module (`evals/frontier_compare/providers.py`) that can make real, live HTTP calls to OpenAI, Anthropic, and a local Ollama install, gated behind operator-supplied API keys and manually-installed SDK packages that are not part of the base install (`openai`/`anthropic` are absent from `pyproject.toml`/`uv.lock`). It is reached only from `evals/frontier_compare/` benchmark scripts and `core/contemplation/miners/frontier_compare.py` (which parses already-generated report *files* offline — no live call). No import of `evals.frontier_compare` exists anywhere in `core/`, `chat/`, `generate/`, `packs/`, or `teaching/` — the serving path CORE actually runs for a user never touches this module. This is a meaningfully different case from Batch 1's ADR-0045 (pure static citation of published frontier numbers): ADR-0082's code path can genuinely dial out, but only when an operator explicitly runs a comparison benchmark with their own credentials — it is eval-time baseline-comparison tooling, not a live serving-path dependency, and README.md's "not an LLM, not an LLM wrapper" claim (which is about how CORE itself generates language) is untouched by its existence. ADR-0098 and ADR-0099 are a tight two-ADR arc: ADR-0098 defines the `DemoCommand` protocol/`DemoResult` contract (`core/demos/contract.py`) so demos can be composed without reimplementation or subprocess-stdout parsing; ADR-0099 consumes it to build `core demo showcase`, a single command that composes four already-shipped demos (register-tour, fabrication-control-public, learning-loop, a new thin multi-hop adapter) into one deterministic JSON+HTML artifact. Both were directly re-executed during this audit: `core demo showcase --json` runs end-to-end and returns `all_claims_supported: true` with all four scenes passing; `tests/test_demo_composition.py` (28/28) and `tests/test_public_showcase.py` (7 passed, 1 structurally-skipped) pass directly; a fresh, ephemeral re-run of the `demo_composition` lane's own runner reproduces the currently pinned SHA exactly (8/8 cases). The one substantive finding is that ADR-0099's own stated hard invariant — "CI fails if showcase exits with `all_claims_supported=False` or runtime >30s" — is no longer true as built: the runtime budget was raised to 60s and then demoted to a **soft**, non-gating check (`CORE_SHOWCASE_HARD_BUDGET=1` opt-in only), and the one test that should catch a regression (`test_runtime_within_budget`) is structurally self-skipping in the shipped test file because its own fixture unconditionally sets `CORE_SHOWCASE_SKIP_BUDGET=1`. This audit's own live run measured 77.7s (over even the revised 60s budget) and the CLI still exited 0 — directly observed, not inferred. The softening is transparently documented in `evals/public_demo/contract.md`'s "Known Environment Caveat" (a rare case of the record and the code agreeing on the drift), which mitigates but does not erase the gap between the ADR's own "Invariant" section and current CI behavior.

### 3. Liveness / integration

- Reached only from `evals/frontier_compare/` benchmark entry points (`__main__.py`, `cross_provider.py`) and from `core/contemplation/miners/frontier_compare.py::mine_frontier_compare_report`, which parses a **pre-generated JSON report file** offline (`json.loads(path.read_text(...))`) — no live provider call. A repo-wide grep for `evals.frontier_compare` imports across `core/`, `chat/`, `generate/`, `packs/`, `teaching/` found none. The serving path CORE actually runs for a chat turn never imports this module. The `openai`/`anthropic` adapter builders further require packages that are not installed in the base environment, so even if something did import `build_adapter`, invoking the `openai`/`anthropic` arms today raises `ImportError` unless an operator installs them by hand.
- **Sabotage test:** if `evals/frontier_compare/providers.py` were deleted entirely, nothing on the live chat/serving path would change — no chat turn, no CLI command other than the benchmark scripts themselves, and no CI gate depends on it (confirmed: `tests/test_frontier_compare_cross_provider.py` and `tests/test_frontier_model_registry_pricing.py` are declared in `tests/full_only_baseline.txt`, in no curated suite — see zone-level finding). Removing it would only break operators who deliberately run a frontier-comparison benchmark by hand. This is the correct, intended shape for an evaluation instrument, not a decoration finding — the module's *purpose* is exactly to be invoked only when someone chooses to run a comparison, and it does what it claims when invoked (confirmed by direct test execution below).
- **Liveness axis:** wired-but-unreached (from the live serving path) / live (from the benchmark-invocation path). Tests `tests/test_frontier_compare_cross_provider.py` (12 tests) and `tests/test_frontier_model_registry_pricing.py` were run directly during this audit: 12 passed.

## ADR-0098 — Demo Composition Contract

**Audit ID (if a numbering collision):** — | **Family (if phased):** — (paired arc with ADR-0099)

### 1. Content summary

- **Decision made:** Introduce `DemoCommand` as a typed protocol (`demo_id`, `claim_contract_version`, `run(*, output_dir, seed=None) -> DemoResult`) plus `DemoResult`/`Claim` dataclasses, so existing demos can be retrofitted (mechanically, same PR) and future demos can implement the contract from the start — enabling a composing demo (ADR-0099) to read another demo's result without reimplementing it or subprocess-spawning it and parsing stdout.

  - Invariants: `demo_composition_no_side_effects`, `demo_json_byte_equality`
